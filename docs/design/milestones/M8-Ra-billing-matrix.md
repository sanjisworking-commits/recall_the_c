# M8-Ra — Billing state / action matrix (for review)

**Why this exists.** The M8-R plan first proposed changing the billing page for an account whose stored period has elapsed while the provider row is still `active`. The owner withdrew that on 2026-11-27: an elapsed stored date does not establish that the provider subscription has ended, and a "Subscribe" treatment could open a duplicate-subscription path or hide a cancellation that is still needed. M8-Ra therefore changes nothing on the billing page and delivers this matrix instead. **Nothing is built from it; it makes no recommendation.**

**How it was made.** `m8/tools/billing_matrix_m8.py` seeds each stored subscription shape into a throwaway local database, renders `/billing/subscriptions`, and then requests each billing route directly (Subscribe to Plus, Subscribe to Pro, Change to Pro, Change to Plus, Cancel), recording the route's redirect, the calls it made to the provider client and the subscription rows afterwards. Full output: `m8ra/02-candidate-2270d77/billing-matrix.json` and `billing-matrix.md` (both tier models).

**What it cannot show.** The provider client is a mock that answers every call with a subscription mirroring the stored row. The matrix shows what the application decides and what it would ask the provider to do. It does not show what Razorpay would answer, whether a mandate is live, whether a payment retry is in progress, or when a change takes effect. **Provider behaviour: NOT RUN.**

Reach: **P** = a stored shape the application's own code can leave; **S** = a synthetic fixture.

## 2. What the matrix shows

1. **"Subscribe" never starts a second subscription beside a live one.** With a current row that is `authenticated`, `active`, `pending`, `halted` or `paused` — whatever the stored period — the create route answers `change_required` and makes no provider call. With an open checkout it returns to that checkout; with a reservation it answers `in_progress`. A new row is created only when there is no current row, or the current row is terminal (in which case the old subscription is fetched first and marked not-current).
2. **Elapsed stored period, row still `active` (H7).** The Playground is read-only ("paid period ended"), and the billing page offers what it offers any active subscriber: "Cancel at cycle end" and the upgrade. Requested, the cancel route asks the provider to cancel at cycle end and the change route asks it to change plan now. "Subscribe" is refused (`change_required`). So the page does not match the Playground's reading of the account — and a "Subscribe" button here, as first proposed, would have been an action the server refuses.
3. **Halted, paused, pending and authenticated accounts have no action at all.** The billing page offers nothing, and all five routes refuse (`change_required`, `state`, `unpaid_cancel`). This is where "Resume Playground" and "Manage subscription" lead from the Playground home, the Act head, the Add sheet, Today, the Calendar and the Profile card. The application gives these accounts no way to resume, retry, cancel or resubscribe; whatever resolves the subscription happens at the provider.
4. **A pending account whose stored period has elapsed** resolves to "paid period ended" (read-only), also with no action.
5. **Cancel is refused unless the row is `active`** (`unpaid_cancel`). For a row already set to cancel at period end the page does not offer Cancel; requested directly, the route calls the provider again and the row is unchanged.
6. **A legacy Max account** is offered "Schedule Plus", "Schedule Pro" (both at cycle end) and Cancel; "Subscribe" is refused.
7. **Fixture against service shape.** A terminal row that is still current (**S**) and a terminal row that is not (**P**) both let "Subscribe" create a new row; they differ in what the account resolves to (read-only "paid period ended" against no subscription) and in the page's heading.

## 3. Questions this leaves for the owner (not proposals)

- **Q-A.** Should the billing page reconcile with the provider before it chooses what to offer, so that "elapsed stored period, active row" is resolved one way or the other (still active with a stale date, or ended) instead of being presented as both?
- **Q-B.** What should a halted, paused or pending account be able to do in the application — retry a payment, update the payment method, cancel, or nothing — and should "Resume Playground" lead somewhere that says which?
- **Q-C.** Should Cancel be available to a halted or paused subscriber (today: refused), given that a mandate may still exist at the provider?
- **Q-D.** For the 5-20 decision: rows 4, 7 and 9 of the proposed table would give halted, paused and cancelled accounts paid access until the verified paid-through date. The billing actions for those states are part of the same decision.

Each answer needs provider behaviour that has not been observed here.
