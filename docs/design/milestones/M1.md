## 2. Review findings that this revision addresses

1. The existing checklist silently excludes login/legal routes listed in the roadmap. Define shell changes and deliberate exceptions separately from protected page bodies.
2. `/login` is standalone `login.html`, explicitly outside `base.html`; it has no shared top nav. M0's description of a legacy login top nav is inaccurate. Preserve the accepted login surface as an explicit exception; do not claim it was converted.
3. Guest `/dashboard` renders a guest dashboard in `auth/routes.py`. Remove the suggestion that its ordinary guest state redirects to login. An invalid existing session is a different state and must retain its session-expired behavior.
4. The public section route is `/laws/{law_id}/section/{number}`, not `/sections/{n}`. Public Act readers use `bareactsection` and `bareactschedule`, not the Constitution reader's `article` screen key. Do not assume identical tab visibility.
5. `mobile.css` hides tab bars for `search` and `settings`. Markup assertions alone would miss this failure. Require rendered visibility, hit testing and keyboard checks.
6. Existing shared viewport metadata disables zoom. Record it explicitly; the proposed shared-shell accessibility scope includes restoring zoom in `base.html`. Login has a separate zoom restriction and remains a disclosed out-of-scope finding, not an accessibility PASS.
7. Signed-in navigation already has route-specific differences. In particular, generic phone Browse matching does not include `/laws`, and Settings/Search/Tables do not all receive a current-tab marker. Preserve this baseline unless separately approved; do not promise both byte-identical signed-in markup and universal corrected active states.
8. `guest_chrome` currently renders a Guest account menu, not the proposed standalone Sign in button. Footer tools include Contact us, Tables and theme functionality. Removing them without preserving access would be a functional regression.
9. M0's full signed-in desktop capture gap cannot be closed with only Dashboard/Browse screenshots. Capture all reachable S1–S11 states, with inaccessible states explicitly recorded.

## 3. Scope and deliberate exceptions — proposed for approval

Goal: consistent guest navigation without redesigning page contents. Close DV-1 and DV-4 only for the enumerated shell surfaces; do not close entire page-family deviations.

Allowed implementation, only after explicit approval:

- Guest shell branches in `web/templates/base.html`: navigation, account entry point, shell spacing and narrowly scoped zoom correction.
- Shell selectors in `web/static/styles.css` and `mobile.css`; cache pins for changed assets. Changes to `playground.css` only if demonstrated necessary for a conflicting shell selector and added to the approved file list first.
- Focused navigation/accessibility/regression tests. Do not weaken existing behavior tests to obtain green results.
- Retain page-specific data attributes unless all CSS/JS dependencies have been inventoried. No wholesale flag deletion. `app.py` context cleanup is unnecessary for M1 and excluded by default.

Protected: page-body templates/copy/layout, legal text, authentication logic, authorization, payments, entitlements, devices, canonical law data, revision calculations, APIs, migrations, environment configuration and dependencies. No page-content flag may be removed just because it also affects chrome.

Recommended exceptions: standalone Landing and Login unchanged; Constitution reader retains its existing phone bar suppression; public Act readers are regression-only pending explicit shell expansion. Keep existing footer functionality and destinations in M1; cosmetic footer simplification belongs in a later approved scope. Legal pages may receive inherited guest chrome, while their bodies and legal links remain unchanged.

Signed-in screens are regression checks, not redesign targets. Do not silently repair their pre-existing active-state gaps or claim they meet the new guest contract.

**Owner-added scope (accepted 2026-10-19):** two shell-level findings from the desktop re-score (M0 report §3.1) are in M1 because they live in the shared shell, not in page bodies:

- **DV-20 — account slot consistency (signed-in, desktop).** The header account slot must render the same way on every shared-shell page: avatar, name and the "Free account" subtitle (or the plan name once subscribed), as the prototype draws it. Today, Calendar, Profile, Settings and Devices currently omit the subtitle; Browse, Laws, NDPS, gate, plans and UAPA show it.
- **DV-21 — main nav on gate, plans and Add (signed-in, desktop).** `/playground` (gate), `/playground?stage=plans[&tier=…]` and `/playground/laws/{id}/add` must render the full top nav (Today / Browse / Playground / Calendar / Profile) with Playground active, instead of brand + account only. The Add presentation itself (standalone page vs modal) is DV-15 and stays in M2; M1 only restores the shell around it.

Both are header/nav changes in `base.html` and the shell CSS; no gate, plan, pricing or entitlement logic changes.
